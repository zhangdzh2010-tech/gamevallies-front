# 私信功能设计方案（个人主页入口 / 抖音式交互）

## 1. 文档目标

本文档用于定义小游戏小程序内的用户私信功能一期方案，重点解决以下问题：

- 私信入口放在哪里最自然
- 个人主页如何参考抖音做“关注 + 私信”双按钮
- 现有“消息”页如何从通知中心升级为“私信 + 通知”双入口
- 前后端需要补哪些页面、数据结构和接口
- 第一阶段应该做到多深，避免功能过重

本文档同时覆盖产品交互、前端页面结构和后端接口草案，供后续实现统一对齐。

---

## 2. 当前现状

基于当前前端仓库，现状如下：

- 当前个人主页是“我的主页”形态，头部只有设置、退出、订阅信息，没有“访客态主页”和“关注”按钮。
- 当前 tabBar 中已经有“消息”入口，但页面实际承载的是通知流，不是用户会话列表。
- 当前前端已接入的消息接口只有通知相关接口，没有用户私信会话与消息发送接口。
- 当前本地 API 文档里也只有通知接口，没有 `/conversations`、`/messages`、`/chat` 一类私信接口。

这意味着私信功能不是“补一个按钮”就能完成，而是需要同时补齐：

1. 他人主页访客态
2. 私信会话列表
3. 聊天详情页
4. 私信接口与未读数能力

---

## 3. 设计结论

### 3.1 入口位置

推荐将私信入口放在“他人主页”的头部操作区，紧挨“关注”按钮右侧，做成抖音风格的双按钮结构：

- 左侧主按钮：`关注` / `已关注`
- 右侧次按钮：`私信`
- 右上角保留 `...` 更多操作位，供后续扩展举报、拉黑、分享主页等功能

不建议把私信入口放在“我的主页”里，原因如下：

- 用户不会给自己发私信
- 会稀释“编辑资料 / 设置”的主操作权重
- 不符合抖音、快手等内容型产品的常见心理模型

### 3.2 消息页结构

推荐将现有 tabBar“消息”页升级为双 Tab：

- `私信`
- `通知`

进入规则：

- 从 tabBar 点击“消息”时，默认进入上次停留的 Tab
- 从他人主页点击“私信”时，直接打开对应聊天详情页
- 聊天返回后，回到“私信”列表，而不是通知流

### 3.3 一期范围

第一期只做最小可用能力：

- 单聊
- 纯文本消息
- 会话列表
- 聊天详情
- 未读数
- 已读状态

第一期不做：

- 图片消息
- 语音消息
- 撤回
- 引用回复
- 群聊
- 表情包商城
- 陌生人复杂权限系统

---

## 4. 个人主页改造方案

## 4.1 页面分态

个人主页需要拆成两种状态：

### A. 我的主页

保留当前逻辑：

- 编辑资料
- 设置
- 退出登录
- 订阅信息
- 我的作品 / 收藏 / 任务等内容

不显示：

- 关注
- 私信

### B. 他人主页

新增访客态头部：

- 头像
- 昵称
- 简介
- 关注数 / 粉丝数 / 获赞数
- 操作按钮行：`关注` + `私信` + `...`
- 作品列表

---

## 4.2 按钮布局建议

参考抖音的小程序/移动端内容主页，推荐按钮布局如下：

```text
[关注/已关注] [私信] [...]
```

设计建议：

- 按钮高度：`80rpx`
- 按钮圆角：`999rpx`
- 按钮间距：`16rpx`
- “关注”按钮权重最大，占比更宽
- “私信”为次级操作，宽度略小于“关注”
- `...` 为圆形图标按钮

视觉建议：

- 页面基底：深色背景
- 主文案：高亮白色
- “关注”按钮：高对比主色实心，接近抖音系红色视觉
- “私信”按钮：深色半透明或描边按钮
- 按钮文字比当前页面整体字号更大一档，保证可触达和可读性

---

## 4.3 状态规则

### 自己看自己

- 不显示“关注”
- 不显示“私信”
- 显示“编辑资料”或“设置”

### 已登录用户看别人主页

- 永远显示“私信”按钮
- 左侧显示“关注”或“已关注”

### 未登录用户

- 点击“关注”或“私信”都先走登录

### 自己看别人但被风控限制

预留禁用态：

- `私信` 置灰
- 提示“暂时无法发起私信”

---

## 5. 消息页改造方案

## 5.1 当前问题

当前“消息”页本质是通知页，承载内容包括：

- 点赞通知
- 评论通知
- 关注通知
- 复刻通知
- 系统通知

如果直接新增私信入口但不改消息页，会出现两个问题：

1. 用户能发起私信，却找不到自己的会话列表
2. “消息”tab 的定位仍然偏通知中心，不像社交消息中心

---

## 5.2 新结构

推荐将 `消息` 页改成两级结构：

### 一级页：消息中心

顶部切换：

- `私信`
- `通知`

### 二级页 A：私信列表

每条会话卡片包含：

- 对方头像
- 对方昵称
- 最后一条消息摘要
- 最后活跃时间
- 未读数红点
- 可选在线状态

### 二级页 B：通知列表

保留现有通知能力即可，不影响当前点赞/评论/关注通知链路。

---

## 5.3 聊天详情页

聊天详情页建议结构：

- 顶部导航：返回、对方头像、昵称、更多操作
- 消息区：左右气泡布局
- 时间分隔
- 底部输入栏：输入框 + 发送按钮

建议行为：

- 进入即自动标记当前会话已读
- 首屏默认滚到底部
- 发送成功后立即本地插入消息，再等待服务端确认
- 发送失败要有重发态

---

## 6. 推荐产品规则

## 6.1 一期推荐规则

推荐第一期采用以下策略：

- 只要登录，就可以发起私信
- 不要求必须互关才能私信
- 但后端必须做频率限制与风控

这样做的原因：

- 转化成本最低
- 与“关注旁边就是私信”的抖音式交互最一致
- 有利于创作者与玩家建立连接

---

## 6.2 后续可升级规则

如果担心骚扰问题，后续可以逐步增加：

- 只允许关注后私信
- 只允许互关后持续聊天
- 陌生人首条消息限制
- 创作者关闭陌生人私信
- 拉黑与举报

这些规则不建议在第一期一次性做满，否则开发量会迅速变大。

---

## 7. 页面跳转流

## 7.1 从他人主页发起私信

```text
他人主页
  -> 点击“私信”
  -> 请求“查找或创建会话”
  -> 跳转聊天详情
```

## 7.2 从消息 tab 进入私信

```text
tabBar 消息
  -> 默认打开“私信”或上次停留 tab
  -> 进入会话列表
  -> 点击某个会话
  -> 打开聊天详情
```

## 7.3 从消息详情返回

```text
聊天详情
  -> 返回
  -> 回到私信列表
  -> 再返回上一页或 tabBar
```

## 9. 后端接口草案

## 9.1 获取会话列表

### 接口

`GET /api/v1/conversations?page=1&limit=20`

### 返回

```json
{
  "code": 0,
  "data": {
    "items": [
      {
        "id": "conv_123",
        "peerUser": {
          "id": "user_456",
          "nickname": "张三",
          "avatarUrl": "https://..."
        },
        "lastMessage": {
          "id": "msg_999",
          "content": "你好",
          "senderId": "user_123",
          "createdAt": "2026-03-27T10:00:00.000Z"
        },
        "unreadCount": 2,
        "updatedAt": "2026-03-27T10:00:00.000Z"
      }
    ],
    "hasMore": false
  }
}
```

## 9.2 查找或创建会话

### 接口

`POST /api/v1/conversations`

### 请求

```json
{
  "targetUserId": "user_456"
}
```

### 返回

```json
{
  "code": 0,
  "data": {
    "conversationId": "conv_123"
  }
}
```

## 9.3 获取会话消息

### 接口

`GET /api/v1/conversations/:conversationId/messages?cursor=&limit=30`

## 9.4 发送消息

### 接口

`POST /api/v1/conversations/:conversationId/messages`

### 请求

```json
{
  "type": "text",
  "content": "你好，想合作测试一下你的游戏"
}
```

## 9.5 标记会话已读

### 接口

`POST /api/v1/conversations/:conversationId/read`

## 9.6 获取私信未读总数

### 接口

`GET /api/v1/conversations/unread-count`

## 10. 实时能力建议

为保证体验接近抖音式消息产品，建议后端提供实时推送能力：

- 新消息推送
- 会话未读数变化推送
- 消息已读回执推送

推荐事件类型：

- `conversation.message.created`
- `conversation.read.updated`
- `conversation.unread.updated`

如果第一期实时链路还没准备好，可先采用：

- 进入列表时拉取一次
- 聊天详情页内定时轮询
- 发送消息后本地乐观更新

---

## 11. 风控与安全

一期至少要有以下约束：

- 未登录不可发私信
- 不允许给自己发私信
- 单用户发送频率限制
- 敏感词拦截或审计预留
- 拉黑能力预留字段

建议后端至少支持以下错误语义：

- `400` 目标用户不存在
- `400` 不能给自己发消息
- `401` 未登录
- `403` 对方禁止陌生人私信
- `429` 发送过于频繁

前端收到这些错误时，直接弹用户可读文案。

## 12. 前端落地拆分

## 12.1 页面改造

需要新增或调整：

- 个人主页新增“他人主页访客态”
- 个人主页头部增加 `关注 + 私信 + ...` 操作区
- `消息` 页改为 `私信 / 通知` 双 Tab
- 新增 `聊天详情页`

## 12.2 Service / Store

建议新增：

- `src/services/message.js`
- `src/stores/messageStore.js`

职责建议：

- `message.js` 只负责接口请求
- `messageStore.js` 负责会话列表、消息列表、未读数、本地乐观更新

## 12.3 路由建议

建议新增：

- `/pages/message/index` 继续保留为消息中心
- `/pages/message/chat/index?conversationId=xxx`

---

## 13. 实施顺序建议

推荐按以下顺序推进：

### 阶段一：结构补齐

1. 他人主页访客态
2. 头部 `关注 + 私信 + ...` 视觉与交互
3. 消息中心改为 `私信 / 通知` 双 Tab

### 阶段二：私信 MVP

1. 会话列表
2. 聊天详情
3. 发送文本消息
4. 已读未读

### 阶段三：体验增强

1. WebSocket 实时推送
2. 红点统一
3. 风控与举报
4. 更多消息类型

---

## 14. 验收标准

一期完成后，应满足以下验收标准：

- 进入他人主页时能看到 `关注 + 私信 + ...`
- 点击“私信”可直接进入会话
- “消息”tab 内可切换 `私信` 与 `通知`
- 私信列表可看到最近会话和未读数
- 聊天详情可发送文本并正确显示时间顺序
- 返回后列表未读数与 tabBar 红点状态一致

---

## 15. 最终建议

最终建议采用以下路线：

- 入口放在“他人主页”关注按钮右侧
- 整体视觉参考抖音，但保留当前产品的深色创作型气质
- 消息页必须同步升级为 `私信 + 通知` 双结构
- 第一阶段只做文字私信，不做重型 IM 功能

这是一条开发成本相对可控、用户感知却足够明显的路线，适合作为当前版本的社交能力升级方向。
