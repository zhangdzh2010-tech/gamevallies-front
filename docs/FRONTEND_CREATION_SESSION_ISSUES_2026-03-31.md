## 一、结论摘要

当前前端已经把 `create / iterate / fork` 三条入口迁移到了 creation session 主链，但从真实线上体验看，前端仍存在一批结构性问题。

这些问题的特点不是“单点 bug”，而是：

- 前端对后端状态波动的容错不够
- active session 残留会被前端明显放大
- 页面交互还没有形成足够稳定的产品语义

换句话说：

- 后端问题决定了“会不会返回稳定会话”
- 前端问题决定了“后端一旦不稳定，用户体验会不会立刻垮掉”

目前前端在第二层还不够强。

## 二、核心问题列表

### 1. 前端仍然围绕“全局唯一 active session”做恢复，天然容易串入口

严重级别：High

当前现状：

- 页面恢复逻辑本质上仍然是先取全局 `active session`
- 再判断这条 session 是不是当前页面想要的
- 如果不匹配，再 reset 或新开

这会带来的问题：

- `create / iterate / fork` 之间会互相争用 active slot
- 用户从一个入口切到另一个入口时，容易被旧上下文拖住
- 后端只要残留一条 active，前端就会受影响

为什么这是前端问题：

- 后端 active 设计确实有限制，但前端没有把这个限制转化成更清晰的用户选择
- 当前实现更像“系统自动猜”，而不是“让用户决定继续上次还是开启新的”

建议修复：

1. 对恢复逻辑增加显式提示层：
   - “检测到你有未完成的创作，继续上次还是开始新的？”
2. 不要把“静默恢复”作为默认唯一方案
3. 在页面级明确区分：
   - 当前入口可恢复的 session
   - 与当前入口无关的 session

### 2. 前端没有真正收口 `status / readyToGenerate / currentQuestion` 的冲突

严重级别：High

当前现状：

- 后端可能同时返回：
  - `status=ready`
  - `readyToGenerate=true`
  - `currentQuestion` 仍存在
- 前端目前只是“把这些都展示出来”
- 没有定义一个唯一主操作

这会带来的问题：

- 用户不知道应该继续回答还是直接生成
- 页面会同时出现“还在问”和“已经可生成”的混合信号
- 会话体验缺乏确定性

为什么这是前端问题：

- 即使后端状态语义不够干净，前端也应该给用户一个明确优先级
- 当前前端没有把这种冲突压成一个产品决策

建议修复：

1. 前端统一定义优先级策略，例如：
   - 若 `readyToGenerate=true`，主按钮永远是“直接生成”
   - `currentQuestion` 降级为“继续补充”
2. 页面上不要并列两个同等级主路径
3. 对这种冲突增加埋点，方便判断真实用户更常走哪条路径

### 3. 会话创建失败时，前端错误恢复不够产品化

严重级别：High

当前现状：

- 一旦 `startCreationSession` 失败
- 前端更多是进入一个工程化 error state
- 用户缺少明确的下一步动作

真实风险：

- 首句提交后直接失败
- 页面停在半初始化态
- 用户不知道该重试、改内容，还是重新开始

建议修复：

1. 为“创建 session 失败”单独设计错误态
2. 至少提供三个明确动作：
   - 重试这次提交
   - 修改首句后重试
   - 返回初始输入态
3. 保留用户首句输入，不要失败后清空

### 4. 首句输入失败或初始化失败时，前端缺少幂等重试与内容保留

严重级别：High

当前现状：

- `create / iterate / fork` 都强依赖首句提交后立即拿到有效 session
- 如果后端慢、失败、波动，页面很容易进入尴尬态

用户体验问题：

- 输入内容可能丢失
- 用户要重新想一遍、再输一遍
- 失败和 loading 的边界不清楚

建议修复：

1. 首句输入在本地暂存，直到 session 创建成功
2. 增加幂等重试：
   - 同一首句在失败后允许直接重试
3. loading 分层更清晰：
   - 提交中
   - 会话创建中
   - 会话已创建，等待补问

### 5. “重新开始”与“继续上次”在前端还没有成为明确产品动作

严重级别：Medium

当前现状：

- 现在更多是工程动作：
  - reset
  - abandon
  - restore
- 这些逻辑在代码里有，但对用户并不透明

这会带来的问题：

- 用户并不知道系统到底是在继续旧会话，还是偷偷新建了一条
- 当 active 残留时，页面行为显得不可预测

建议修复：

1. 页面显式提供：
   - 继续上次创作
   - 开始全新一轮
2. 对“重新开始”定义明确语义：
   - 是否 abandon 当前会话
   - 是否保留首句
   - 是否回到初始引导页

### 6. 当前页面壳虽然重做了，但会话层和页面层仍然有脱节

严重级别：Medium

当前现状：

- 三页视觉已经比旧版好很多
- 但底层仍然是偏工程状态机驱动
- 一旦状态不稳定，页面就会露出“半成品”感

表现：

- loading 态偏硬
- 错误态偏工程
- 状态切换时跳跃感明显
- 用户很难形成“我现在正处在哪个阶段”的稳定认知

建议修复：

1. 明确三种页面阶段：
   - 首句输入
   - 会话打磨
   - 生成中/生成后
2. 每个阶段只保留一个主要目标
3. 不把工程状态直接暴露为用户状态

## 三、按页面拆分的问题

### 1. `create`

当前主要问题：

- 首次创建失败时缺少强恢复能力
- `ready` 与继续追问并存时，主操作不明确
- active session 残留会直接影响再次创作

建议优先级：

1. 会话创建失败重试
2. ready/继续补问优先级收口
3. 继续上次/开始新的选择层

### 2. `iterate`

当前主要问题：

- 同一作品多轮优化时，状态不稳定
- 用户不容易区分：
  - 是继续上一轮优化
  - 还是开始本轮新优化
- 生成中 session 仍可能阻塞下一轮

建议优先级：

1. 当前作品的会话身份明确化
2. 生成中与新一轮优化解耦
3. 继续上次/开启新一轮显式选择

### 3. `fork`

当前主要问题：

- 目前流程能跑，但仍受全局 active session 模型影响
- 如果 sourceGameId 对应会话未清理，前端很容易被旧会话拖偏

建议优先级：

1. `sourceGameId` 维度的恢复提示
2. fork 首句失败后的重试
3. fork 会话残留处理

## 四、建议的前端整改顺序

建议按下面顺序推进：

### 第一阶段：状态与容错收口

目标：

- 不再让后端轻微波动直接把页面体验打崩

要做的事：

1. 首句输入本地保留
2. 会话创建失败专门错误态
3. 重试机制
4. ready 与 question 冲突收口

### 第二阶段：恢复与重启产品化

目标：

- 把当前工程化 restore/reset/abandon 变成用户可理解的动作

要做的事：

1. 继续上次 / 开始新的选择层
2. 重新开始语义统一
3. 入口间 session 身份隔离更清晰

### 第三阶段：页面阶段一致化

目标：

- 让 `create / iterate / fork` 真正共享一套可理解的会话体验

要做的事：

1. 三阶段页面模型统一
2. loading / error / generating / completed 的视觉和文案统一
3. 减少工程态直出

## 五、建议直接拆成的任务

下面这些可以直接进迭代排期：

1. `create / iterate / fork` 首句输入失败后保留内容并支持一键重试
2. 新增“检测到未完成创作，继续还是重新开始”弹层
3. 收口 `readyToGenerate + currentQuestion` 的主操作逻辑
4. 把 session 创建失败、session 恢复失败、session 冲突分别做独立错误态
5. 统一三页的 loading 和阶段提示
6. 增加 session 生命周期相关埋点

## 六、建议与后端联动的契约点

前端整改时，需要后端至少明确这些点：

1. active session 是否全局唯一
2. generating 中的 session 是否仍算 active
3. `readyToGenerate=true` 时是否允许继续追问
4. `status=ready` 的正式定义
5. create 偶发 `400` 的原因与错误码

## 七、一句话判断

当前前端最大的问题不是“界面不好看”，而是：

- 页面层已经像产品
- 但状态层还更像工程调试界面

只要把“恢复、失败、冲突、重试”这几层真正产品化，哪怕后端还有波动，用户体验也会稳定很多。
